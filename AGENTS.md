# Architecture rules
- Race-day record context must match the selected car and weekend; reusable review pages receive route input through props, and lap mutations capture their session before asynchronous saves.
- Keep the public product walkthrough isolated from authenticated workflow components; the landing preview is static illustrative data only — never predictions of pressures, handling or lap times, and never real account data.
- Keep launch validation rules in a shared client-safe module so account confirmation and AI input limits can be tested independently.
- All AI gateway calls consume the same atomic, service-role-only per-user UTC-day quota before sending a request; attempted calls count even if the provider fails.
- Account deletion uses an authenticated server function, derives the target from the verified caller, cleans storage and application data, then deletes the auth user; owned cars and their shared records are deleted, not transferred.
- Offline support uses vite-plugin-pwa generateSW and one guarded registration wrapper; never register in development, preview, iframes, or localhost.
- Keep branded page metadata on leaf routes; root holds only sitewide defaults.
- Profile reads are limited to the caller's own profile and crew on cars they own; sharing must not expose unrelated profiles.
- Support submissions send independent, event-deduplicated team and sender emails after durable storage; team alerts use authenticated role-checked polling so notifications cannot expose messages to other users.
- Personal inbox data uses participant-scoped RLS; crew discovery returns only names and IDs of shared-car members, while support assignment and the support roster require a verified admin role. Direct messages permit recipient-only read receipts, and support replies stay within their original request's access boundary.
- Stored support team replies send one event-deduplicated email to the original request's recipient after verifying the caller's role; delivery failures and suppression must be distinguished from successful sends so staff do not mistake storage for delivery.
- Tyre identity lives in `tyre_sets` + `tyre_assignments` (slot→position with fitted/removed timestamps so rotations preserve history); readings stay in `tire_logs` linked by `tyre_set_id`, and all tyre analysis is pure functions in `src/lib/tyre-analysis.ts` that emit observations, never definitive setup recommendations.
- Historical setup retrieval is pure logic in `src/lib/setup-retrieval.ts` (same car + circuit required, conditions only re-rank); "use as starting setup" always inserts a new setups row naming its source and never overwrites the original, and empty history must show a clear message rather than suggestions.- Handling-issue assistant logic is pure functions in `src/lib/handling-assistant.ts` (causes capped at 3, one recommended test, missing data listed, never invented); braking/suspension/stability issues are safety-critical and require acknowledgement, and recommendations save as `handling_recommendation` timeline events with proposed/verified/rejected status — never mutate recorded setups.
- Engineering calculators are pure validated functions in `src/lib/calculators.ts` (return null on invalid input, never divide by zero, never invent values; formulas and assumptions shown in UI); vehicle gearbox info persists on `cars.gearbox` JSONB, and tyre target pressures are never predicted without tyre-specific data.
